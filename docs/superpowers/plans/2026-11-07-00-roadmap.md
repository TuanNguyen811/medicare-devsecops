## Quy ước chung

- Nhánh: `main` được bảo vệ. Làm việc trên `feat/<mảng>-<mô-tả>`, ví dụ `feat/app-patient`, merge qua Pull Request, cần 1 người duyệt.
- Commit theo Conventional Commits: `feat:`, `fix:`, `test:`, `docs:`, `ci:`, `chore:`.
- Python 3.12, quản lý bằng `uv`. Mỗi thư mục `app/`, `agent/`, `benchmark/` là một project `uv` riêng.
- Phiên bản các công cụ quét được khai báo **ở một nơi duy nhất**: `security/tool-versions.env`. CI (kế hoạch B) và benchmark (kế hoạch D) cùng đọc file này.
- **Không bao giờ** thêm comment chặn cảnh báo (`# nosec`, `# nosemgrep`, `# noqa: S…`) vào `app/`. Phát hiện trên bản sạch là dữ liệu FP của thực nghiệm. Chặn cảnh báo sẽ làm sai lệch kết quả.

## Hợp đồng 1: cấu trúc ứng dụng mà công cụ của Agent dựa vào (A → C)

- Mã nguồn ở `app/medicare/<module>/`, với `router.py` (khai báo `APIRouter` và route qua decorator `@router.get/post(...)`), `service.py`, `models.py`, `schemas.py`.
- Phân quyền theo vai trò ở route: tham số `user: User = Depends(require_roles(Role.X, ...))` hoặc `Depends(get_current_user)`, import từ `medicare.common.auth`.
- Phân quyền theo đối tượng (quyền sở hữu, khoa, phân công): **chỉ** gọi qua các hàm `can_*` trong `app/medicare/policy.py`. Docstring mỗi hàm ghi mã quy tắc `R-xx` mà nó thực thi.
- Mọi lần truy cập bệnh án đều gọi `medicare.audit.service.log_access(...)`.
- Quy tắc nghiệp vụ nằm ở `docs/security-requirements.md`, mỗi quy tắc một tiêu đề dạng `### R-xx: <tên>`.

## Hợp đồng 2: Pipeline ↔ Agent (B ↔ C)

**Đầu vào Agent:** mỗi công cụ quét ghi SARIF 2.1.0 vào `sarif/<tool>.sarif`, với `<tool>` ∈ `semgrep, codeql, bandit, trivy, gitleaks, checkov, zizmor`. Agent đọc mọi `sarif/*.sarif` (tên công cụ = tên file), giống gate. Thiếu file nào thì coi như công cụ đó không có phát hiện.

**Lệnh chạy:**

```
uv run --project agent secagent \
  --mode ci|cli|benchmark \
  --repo <đường dẫn repo> --base <sha gốc> --head <sha PR> \
  --sarif-dir sarif --requirements docs/security-requirements.md \
  --out out [--strategy agent|single-shot] [--no-requirements] [--no-ast-tools] [--thinking]
```

**Biến môi trường:** `LLM_API_KEY` (bắt buộc), `LLM_PROVIDER` (`deepseek` mặc định, `openai`, `gemini`, `anthropic`, `openai-compatible`), `LLM_MODEL`, `LLM_BASE_URL` (mặc định theo nhà cung cấp), `LLM_TEMPERATURE`. `secagent` không cần `GITHUB_TOKEN` và không tự gọi API GitHub: job `agent-comment` (không checkout code) gửi `report.md` và `review.json` lên PR.

**Đầu ra trong `out/`:** `report.json`, `report.md` (nội dung comment trên PR), `agent.sarif` (category `ai-agent`), `review.json` (review có comment `suggestion`, chỉ khi có bản vá phù hợp), `trace.jsonl`. Workflow ghi thêm `out/agent-exit` (mã thoát của `secagent`) để job quality-gate đọc.

**Kiểm chứng bản vá** chạy ở job riêng `validate-patches`, không tham chiếu secret, sau khi `agent-report` đã được upload. Quality gate chỉ đọc artifact `agent-report`; artifact `agent-validation` của job này chỉ dùng để hiển thị trên comment. Lệnh: `uv run --project agent secagent-validate --out out --repo . --head <sha PR> [--max-patches 2]`. Lệnh này cập nhật `fix.validated` / `fix.validation_note` trong `report.json` và sinh lại `report.md`, luôn thoát 0 (gate không đọc `validated`).

**Mã thoát:** `0` = chạy xong (dù có lỗ hổng hay không) · `2` = Agent thất bại, gate quay về chế độ `traditional`.

**`report.json`:**

```json
{
  "meta": {"model": "deepseek-chat", "strategy": "agent", "started_at": "ISO-8601",
           "duration_s": 0.0, "llm_calls": 0, "tool_calls": 0,
           "tokens_in": 0, "tokens_out": 0, "cost_usd": 0.0,
           "step_limit": 0, "limit_hit": false, "uncovered_before_check": 0},
  "findings": [ /* đúng schema mục 4.3 của spec; phát hiện mới có source = "agent" */ ]
}
```

**Mã định danh phát hiện (finding id):** cả gate và Agent tính giống hệt nhau cho mỗi kết quả SARIF:
`"<tool>:<ruleId>:<đường dẫn tương đối từ gốc repo, dấu />:<startLine hoặc 0>"`. Đường dẫn được chuẩn hóa theo thứ tự: đổi `\` thành `/`, bỏ `file://`, giải mã percent-encoding (`%20` → dấu cách, `%C3%A2` → `â`), bỏ tiền tố workspace (`/github/workspace/`, `$GITHUB_WORKSPACE/`) và bỏ `./` ở đầu. Tham chiếu: `normalize_path` trong `security/gate/gate.py`.

Mỗi phần tử trong `report.json → findings` có thêm trường `finding_ids: [...]`, liệt kê các finding id của công cụ quét mà kết luận này bao trùm. Agent gộp trùng nên một kết luận có thể bao nhiều id. Phát hiện mới do Agent tự tìm có `finding_ids: []`.

**Quality gate** (kế hoạch B) chỉ đọc `report.json` và các file SARIF, không import code của Agent. Ở chế độ `ai-assisted`, gate xử lý như sau:
- Một phát hiện High/Critical của công cụ quét **không có** trong `finding_ids` của bất kỳ kết luận nào thì bị coi như chưa được thẩm định → **chặn** (fail-safe).
- Kết luận `FP` chỉ miễn chặn phát hiện **Critical** khi PR có label `security-reviewed`.
- Nếu nhiều kết luận cùng bao một finding id thì kết luận khác `FP` thắng (một kết luận `TP` hoặc `NEEDS_REVIEW` là đủ để chặn).

## Hợp đồng 3: kịch bản benchmark (A, C → D)

- `benchmark/scenarios/<Sxx-tên>/patch.diff`: áp được bằng `git apply` lên commit ghi trong `benchmark/BASE_COMMIT`.
- `benchmark/scenarios/<Sxx-tên>/scenario.yaml`: `{id, title, feature, split: dev|test, kind: vuln|decoy|robustness}`.
- `benchmark/ground_truth.yaml`: định dạng như spec mục 5.2.
- Người 1 viết patch cho các kịch bản vì nắm rõ ứng dụng nhất. Người 3 không được xem đáp án của tập test trong lúc tinh chỉnh prompt.
